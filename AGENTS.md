# Правила работы над проектом

## Базовый контекст

Проект — локальная система видеопоздравлений для мероприятий. Все требования первой версии описаны в `SPEC.md`. Архитектурные решения и уточнения зафиксированы в `ARCHITECTURE.md`.

Перед изменением поведения нужно читать оба документа.

## Обязательные инварианты

- Сервер управляет очередью и текущим показом.
- Панель оператора и экран трансляции не выбирают следующий ролик самостоятельно.
- SQLite хранит долговременное состояние: мероприятия, настройки, модерацию, очередь, историю и стену.
- Telegram-токен и другие секреты остаются только на сервере.
- Секреты не передаются в браузер, не пишутся в логи и не попадают в Git.
- Обработка видео не блокирует HTTP API, WebSocket и управление показом.
- Повторный показ создаёт новый `QueueItem`.
- Устаревшие playback-события не должны продвигать очередь.
- Изменения поведения требуют обновления `SPEC.md`, `ARCHITECTURE.md` или README-документации.

## Границы текущей реализации

Не добавлять раньше времени:

- облачный сервер;
- вебхуки Telegram;
- управление с телефона по Wi-Fi;
- ИИ-модерацию;
- анимированную видеостену;
- экспорт архива одной кнопкой;
- сложные декоративные анимации, которые задерживают проверку основной логики.

## Последовательность разработки

Разработка должна идти этапами из `SPEC.md`:

1. Каркас.
2. Приём.
3. Подготовка.
4. Очередь.
5. Экран.
6. Панель.
7. Стена.
8. Надёжность.
9. Простой запуск.
10. Визуальные темы.
11. Desktop-оболочка Electron.
12.1. Portable Windows EXE.
12.2. macOS demo: общие исходники, нативная сборка на macOS, ZIP с `.app`.

Каждый этап должен завершаться работающим результатом и краткой инструкцией проверки.

Нельзя смешивать этапы без причины. Например, на этапе каркаса не нужно реализовывать Telegram, FFmpeg и полноценное оформление.

## Работа с данными

Не использовать один общий статус для всех этапов.

Разделять:

- preparation status для скачивания и обработки;
- moderation status для решения оператора;
- queue/playback status для конкретного показа.

Пути к файлам должны быть относительными внутри `data/`.

Пользовательский ввод, имена гостей и Telegram-имена нельзя использовать как имена файлов.

Файлы, доступные для показа, должны появляться в постоянной папке мероприятия только после успешной подготовки.

## Очередь и воспроизведение

Сервер — единственный источник истины.

Команды должны быть безопасны при повторе. Повтор команды или события не должен приводить к двойному запуску, двойному одобрению, потере элемента очереди или двойному добавлению на стену.

Для каждого запуска ролика сервер создаёт уникальный `playback_id`.

События завершения принимаются только для текущего `playback_id`.

После перезапуска незавершённый ролик возвращается в очередь, а показ остаётся остановленным.

## Принятые уточнения команд

- `Пауза` только приостанавливает текущий ролик без перехода к следующему.
- `Продолжить` снимает паузу с текущего ролика.
- `Запустить` запускает очередь из остановленного или ожидающего состояния.
- `Пропустить` переводит текущий `QueueItem` в `skipped` и не добавляет ролик на стену.
- `Остановить показ` возвращает текущий ролик в начало очереди и останавливает общий показ.
- `Показать повторно` создаёт новый `QueueItem` в конце очереди.

## Telegram и лимиты

В первой версии принимать только `video_note`.

Повторная доставка одного Telegram-сообщения не создаёт новую запись. Уникальность должна быть по Telegram chat ID и message ID.

Повторная отправка того же видео отдельным сообщением считается новой отправкой.

Технически отклонённые сообщения не должны расходовать лимит гостя. Точное правило подсчёта лимита нужно закрепить в тестах при реализации Telegram-приёма.

## WebSocket и snapshot

WebSocket используется для обновлений интерфейса, но не является единственным источником истины.

Клиент при подключении получает snapshot с версией состояния.

После reconnect клиент обязан запросить актуальный snapshot через HTTP.

Если есть сомнение между локальным состоянием клиента и сервером, серверное состояние всегда главное.

## Тестирование

Ключевая логика должна иметь автоматические тесты:

- дедупликация Telegram-сообщений;
- переходы модерации;
- порядок очереди;
- повторные и устаревшие playback-события;
- восстановление после перезапуска;
- повторный показ через новый `QueueItem`;
- отсутствие дублей на стене.

Реальный Telegram, браузерный звук, проектор и второй монитор проверяются вручную.

Windows- и macOS-поставки используют общую серверную логику. Не копировать проект в отдельную
ветку исходников для Mac. Нативные backend/FFmpeg должны соответствовать архитектуре поставки;
Windows `.exe` не включать в `.app`. Сборка и GUI smoke для Mac выполняются на macOS.
Пользовательские `.env`, данные и готовые архивы не загружаются в Git.

## Документация

При изменении поведения обновлять документацию в том же изменении.

Минимально поддерживать:

- `SPEC.md` — требования;
- `ARCHITECTURE.md` — устройство приложения и принятые решения;
- `AGENTS.md` — правила работы над проектом;
- `README.md` — установка, настройка и запуск после появления каркаса;
- `.env.example` — пример конфигурации без секретов после появления каркаса;
- инструкцию подготовки ноутбука к мероприятию после появления процесса запуска.

## Что делать при противоречиях

Если `SPEC.md` и код расходятся, сначала выяснить, что является актуальным требованием.

Если найдено новое противоречие в ТЗ, не прятать его в коде. Зафиксировать решение в `ARCHITECTURE.md` и при необходимости обновить `AGENTS.md`.

Если изменение может повлиять на приёмку, явно указать это в итоговом сообщении и добавить проверку.
