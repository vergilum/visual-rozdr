# Архитектура

## Цель первой версии

Первая версия — локальное приложение для одного ноутбука, одного Telegram-бота, одного активного мероприятия и одного активного экрана трансляции.

Приложение должно работать без публичного сервера, домена и вебхуков. Интернет нужен только для получения новых сообщений и скачивания файлов из Telegram. Уже подготовленные ролики должны показываться без интернета.

## Компоненты

| Компонент | Решение | Ответственность |
| --- | --- | --- |
| Backend | Python + FastAPI | HTTP API, WebSocket, состояние, SQLite, файлы, управление очередью |
| Telegram bot | aiogram long polling | `/start`, `/help`, приём `video_note`, ответы гостю |
| Video worker | фоновые задачи backend-процесса | скачивание, ffprobe, FFmpeg, превью, перенос файлов |
| Admin UI | React + TypeScript, маршрут `/admin` | управление мероприятием, модерацией, очередью и настройками |
| Screen UI | React + TypeScript, маршрут `/screen` | полноэкранное ожидание, один активный ролик, стена превью |
| Storage | SQLite + локальные файлы | долговременное состояние и медиафайлы |

Все компоненты первой версии работают на одном ноутбуке. Electron управляет окнами и жизненным циклом backend-процесса; FastAPI остаётся единственным источником состояния и отдаёт React-интерфейс по loopback HTTP.

## Главные архитектурные правила

- Сервер является единственным источником истины для очереди, текущего показа и состояния мероприятия.
- Панель и экран не выбирают следующий ролик самостоятельно.
- Все долговременные состояния сохраняются в SQLite.
- Все изменения очереди, модерации и playback-состояний выполняются транзакционно.
- WebSocket используется для быстрых обновлений, но не заменяет HTTP snapshot.
- После разрыва WebSocket клиент обязан запросить полный актуальный snapshot.
- Токены и секреты остаются только на сервере.
- Обработка видео не блокирует API, WebSocket и управление показом.
- Файлы становятся доступными для показа только после успешной подготовки и атомарного переноса из временного хранилища.

## Серверный процесс

Один процесс запускает:

- FastAPI HTTP API;
- WebSocket endpoint для `/admin` и `/screen`;
- aiogram long polling как фоновую задачу;
- ограниченную очередь фоновой обработки видео;
- периодические задачи диагностики, очистки временных файлов и восстановления незавершённых работ.

В первой версии запрещено запускать два процесса приложения одновременно. Это важно, чтобы два процесса не читали Telegram, не меняли очередь и не создавали конфликтующие playback-сессии.

Для защиты от случайного двойного запуска нужно добавить lock-файл или SQLite-based application lock на этапе реализации каркаса.

## Модель данных

Статусы подготовки, модерации и показов должны быть разделены. Нельзя вводить один общий статус поздравления.

Основные сущности:

- `Event` — мероприятие, код подключения, настройки, состояние приёма, признак активности.
- `GuestBinding` — Telegram user ID и выбранное мероприятие.
- `EventTable` — настроенный оператором стол мероприятия: номер и необязательное задание.
- `PendingTableSelection` — временная запись Telegram-видео до выбора стола; удаляется через 15 минут, не запускает подготовку и не расходует лимит.
- `Submission` — входящее поздравление, отправитель, Telegram chat/message IDs, снимок номера стола и задания, пути файлов, длительность, preparation/moderation статусы.
- `QueueItem` — отдельное воспроизведение конкретного `Submission`, позиция и playback статус.
- `WallItem` — операторски выбранный элемент стены: мероприятие, `Submission`, позиция на стене.
- `PlaybackSession` — активный экран, идентификатор текущего воспроизведения, состояние и heartbeat.
- `AuditEntry` — операторские и системные действия.

Подготовка: `received` → `downloading` → `processing` → `ready`, при ошибке `failed`.

Модерация: `pending`, `approved`, `rejected`.

Показ: `queued`, `playing`, `completed`, `skipped`, `failed`, `cancelled`.

Повторный показ всегда создаёт новый `QueueItem`. История предыдущих показов не перезаписывается.

Стена строится по `wall_items`. Оператор добавляет только ready+approved `Submission`; завершение ролика не добавляет его на стену автоматически. Повторный показ не создаёт второй экземпляр на стене.

## Принятые уточнения к ТЗ

В ТЗ есть несколько мест, которые требуют точной интерпретации при реализации.

1. Команда `Пауза` должна только приостанавливать текущий ролик без перехода к следующему. Иначе она конфликтует с командой `Продолжить`.
2. Команда `Запустить` запускает очередь из состояния `stopped` или `idle`. Команда `Продолжить` снимает паузу с текущего ролика.
3. Команда `Остановить показ` останавливает текущий ролик, возвращает его в начало очереди и переводит общий показ в остановленное состояние. Ролик не добавляется на стену.
4. Команда `Пропустить` передаёт ожидаемый `playback_id`, переводит только совпадающий текущий `QueueItem` в `skipped`, не добавляет его на стену и переходит к следующему ролику, если показ запущен. Повтор той же команды не затрагивает следующий ролик.
5. Команда `Показать повторно` создаёт новый `QueueItem` в конце очереди, а не возвращает старый.
6. Лимит гостя считается по технически принятым поздравлениям, которые не были отклонены из-за скачивания, размера, длительности или ошибки обработки. На этапе реализации нужно закрепить точное правило в тестах.
7. Для ситуации «недостаточно места» нужен конфигурируемый порог свободного места. Начальное решение: `MIN_FREE_DISK_MB=1024` в `.env.example`.
8. Локальная сессия доступа для `/admin` и `/screen` в первой версии может быть простой cookie/session token, созданной сервером при запуске. Секрет не должен попадать в Git.

## HTTP API

HTTP API используется для команд и получения снимка состояния.

Минимальные группы endpoint-ов:

- состояние: `GET /api/state`;
- диагностика: `GET /api/health`, `GET /api/diagnostics`;
- мероприятия: создание, выбор активного, обновление настроек;
- столы: настройка от 1 до 15 столов и заданий мероприятия;
- приём: открыть/закрыть приём сообщений;
- модерация: одобрить, отклонить, одобрить все ожидающие с подтверждением;
- submissions: обновление имени, retry, полное удаление с подтверждением;
- submissions: исправление номера стола только у конкретного ролика;
- очередь: reorder, remove, replay;
- стена: add/remove wall item, запуск выбранного wall submission;
- показ: start, pause, resume, skip, stop;
- экран: регистрация активного экрана и playback events;
- файлы: локальная выдача prepared video, thumbnail, background.

Повтор команды не должен ломать состояние. Для критичных команд нужно использовать идемпотентность через текущую версию состояния, command id или проверку допустимого перехода статуса.

## WebSocket

WebSocket используется для уведомлений:

- изменение очереди;
- новый submission;
- изменение статуса подготовки;
- изменение модерации;
- изменение текущего playback;
- диагностика;
- состояние активного экрана.

При подключении клиент получает snapshot с номером версии. После reconnect клиент повторно запрашивает `GET /api/state`.

WebSocket-событие не должно быть единственным источником истины для клиента. Если клиент пропустил событие, snapshot должен полностью восстановить UI.

С этапа 6 `GET /api/state` возвращает не только активную очередь, но и данные панели оператора:

- `history` — последние завершённые, пропущенные, отменённые и ошибочные `QueueItem` активного мероприятия;
- `failed_submissions` — технически ошибочные поздравления для повторной обработки;
- `screen.progress_sec` и `screen.duration_sec` — прогресс текущего ролика, полученный от активного экрана через heartbeat;
- диагностику `ffmpeg`, `ffprobe`, Telegram-бота, обработчика видео и активного экрана.

Панель оператора не вычисляет завершение ролика по таймеру и не выбирает следующий ролик. Прогресс используется только для отображения.

## Управление экраном

Разрешён только один активный экран воспроизведения.

Экран `/screen` должен зарегистрироваться на сервере. Если активный экран уже есть и heartbeat свежий, новая вкладка получает состояние `secondary` и не запускает звук. После освобождения или потери активного экрана первый heartbeat вторичного экрана переводит его в `active`.

В реализации этапа 5 экран использует:

- `POST /api/screen/register` — регистрация вкладки экрана и получение статуса `active` или `secondary`;
- `POST /api/screen/{screen_id}/heartbeat` — heartbeat и диагностическое состояние экрана;
- `POST /api/screen/{screen_id}/release` — освобождение активного экрана при закрытии вкладки.

Активность экрана хранится в `playback_sessions`. Свежесть heartbeat определяется настройкой `SCREEN_HEARTBEAT_TIMEOUT_SEC`. При потере активного экрана сервер возвращает текущий `playing` элемент в `queued`, очищает его `playback_id`, нормализует очередь и переводит мероприятие в `stopped`.

Для каждого запуска ролика сервер создаёт уникальный `playback_id`. Экран отправляет события только с этим ID:

- started;
- paused;
- completed;
- error.

Сервер принимает `completed` только для текущего `playback_id`. Повторные или устаревшие события игнорируются и логируются.

В реализации этапа 5 playback-события принимает `POST /api/events/{event_id}/playback/events` с полями `type`, `playback_id`, необязательными `reason` и `screen_id`. События `completed` и `error` меняют очередь только если `playback_id` совпадает с текущим `QueueItem`. Если `screen_id` передан, событие принимается только от активного экрана.

Состояние показа хранится в `events.playback_state`: `stopped`, `running`, `paused`, `idle`. `idle` означает, что сейчас нет активного ролика, но это не считается ручной остановкой. Пока оператор не нажал «Остановить показ», сервер создаёт новый `QueueItem` только для готового одобренного ролика, который всё ещё есть на операторской стене. Разовый повтор вне стены завершается один раз и не становится частью автоматического цикла. Удаление ролика со стены не прерывает уже идущий ролик, но исключает его из последующих loop-элементов.

`/screen` не выбирает следующий ролик. Он исполняет `GET /api/state` и WebSocket snapshot: запускает только `playback.current`, ставит видео на паузу при `paused`, останавливает старое видео при `stopped`, `skip` или смене `playback_id`, и отправляет `completed` только из реального `video.ended`. Клиент применяет snapshot только с версией не ниже уже известной и после reconnect получает HTTP snapshot до снятия сообщения о потере связи.

Heartbeat экрана отправляется устойчивым интервалом, а не в ответ на каждый полученный snapshot. Terminal playback-события `completed` и `error` повторяются с тем же `playback_id` до подтверждения сервером либо до смены текущего ролика; серверная идемпотентность не позволяет этим повторам продвинуть очередь дважды.

В browser-режиме экран сразу пытается выполнить `video.play()` по серверной команде, без предварительной подготовки и обязательного клика на `/screen`. Панель не блокирует запуск из-за отсутствия первого клика. Только фактический отказ `NotAllowedError` переводит диагностику в `autoplay_blocked`: экран показывает существующую кнопку «Запустить показ» для повторной попытки непосредственно из пользовательского клика, не отправляет `error` и не продвигает очередь. `AbortError` прерванного запуска не считается отказом autoplay. Отдельной кнопки подготовки нет. Electron использует выделенный `ScreenWindow` с политикой `no-user-gesture-required` и тот же серверный сценарий запуска.

Heartbeat активного экрана также передаёт текущую позицию и длительность видео. Эти значения не являются источником истины для продвижения очереди.

При потере heartbeat активного экрана сервер останавливает продвижение очереди. После перезапуска сервера или экрана незавершённый ролик возвращается в очередь, а общий показ остаётся остановленным до команды оператора.

## Очередь и переходы

Очередь содержит только `QueueItem` и используется как плейлист конкретных запусков: повторов, текущего запуска со стены и циклических элементов автопоказа.

У мероприятия есть `playback_mode`:

- `auto_loop` — автопоказ, сервер создаёт технические `QueueItem` из `wall_items` и повторяет их по кругу;
- `interactive_wall` — интерактивная стена, `/screen` отображает `wall_items`, а клик по шарику отправляет серверную команду запуска конкретного `Submission` со стены.

Одобренный `Submission` может иметь несколько `QueueItem`, если оператор добавил повторный показ или если сервер создал новый элемент для циклического показа.

Ожидающие `QueueItem` имеют позицию. Изменение порядка применяется только к ожидающим элементам и выполняется транзакционно. Циклические повторы помечаются `is_loop`. Позиция стены хранится отдельно в `wall_items.position`.

При успешном завершении текущего ролика сервер:

1. Проверяет `playback_id`.
2. Переводит текущий `QueueItem` в `completed`.
3. Создаёт следующий технический `queued` `QueueItem` из `wall_items`, если показ остаётся запущенным.
4. Не меняет состав стены автоматически.
5. Выбирает следующий `queued` элемент, если общий показ остаётся запущенным.
6. Если `queued` элементов нет, создаёт циклические элементы из операторской стены.
7. Создаёт новый `playback_id` для следующего ролика или переводит экран в ожидание, если циклический показ невозможен.

В режиме `interactive_wall` естественное завершение HTML-видео не отправляется серверу. Экран оставляет ролик открытым и может запускать его повторно локально. Только клик по крестику отправляет `completed` для текущего `playback_id`; после этого технический `QueueItem` попадает в историю, скрывается из видимой очереди стены, а `playback_state` становится `idle`.

Клик по шарику обрабатывает `POST /api/submissions/{submission_id}/play-now`. Команда принимается только для активного экрана, только для `Submission`, который есть в `wall_items`, и только в режиме `interactive_wall`.

Панель оператора может запустить конкретный `Submission` со стены через `POST /api/submissions/{submission_id}/admin-play-now`. Сервер принимает команду только для ready+approved элемента стены, при свежем активном экране и при отсутствии текущего `playing` ролика. Команда создаёт новый обычный `QueueItem` с уникальным `playback_id`; она не прерывает текущий показ. В панели кнопка «Запустить» блокируется с подсказкой «Сначала остановите или пропустите текущий ролик», пока есть текущий ролик.

Удаление ожидающего элемента из очереди переводит его `QueueItem` в `cancelled` и скрывает из истории панели, потому что действие означает удаление из плейлиста, а не состоявшийся показ. Повторный и циклический показ всегда создают новый `QueueItem`.

Очистка истории (`POST /api/events/{event_id}/history/clear`) помечает terminal `QueueItem` как `hidden_from_history`. Она не удаляет submissions, файлы, активную очередь и стену.

Полное удаление `Submission` (`DELETE /api/submissions/{submission_id}`) доступно из очереди, истории, стены, ошибок подготовки и принятых кружочков. Оно удаляет запись, связанные `QueueItem`, историю, `WallItem` и подготовленные файлы. Команда запрещена только если ролик сейчас `playing`; оператор сначала должен остановить или пропустить текущий показ.

Переключение активного мероприятия во время незавершённого показа запрещено. Оператор должен сначала выполнить `Остановить показ`, чтобы очереди разных мероприятий не смешивались.

## Панель оператора

Этап 6 делает `/admin` рабочей панелью оператора. Панель использует серверные API и snapshot, не дублирует правила очереди в React.

Основные блоки:

- мероприятие: создание, выбор, приём, ссылка и QR-код;
- столы и задания: число столов от 1 до 15 и необязательное задание каждого;
- сейчас на экране: текущий `QueueItem`, превью, прогресс от `/screen`, команды показа;
- на проверке: muted-предпросмотр, изменение имени, одобрение, отклонение, массовое одобрение;
- очередь: текущий ролик отдельно, reorder/remove только для `queued`;
- история: terminal `QueueItem`, повторный показ через новый элемент и очистка журнала без удаления файлов;
- стена: текущие выбранные оператором превью, добавление/удаление элемента со стены;
- стена: запуск конкретного ролика на свободный активный экран без прерывания текущего показа;
- принятые кружочки: список только активного мероприятия, предпросмотр, повтор, добавление на стену и полное удаление;
- метки и фильтр столов в модерации и списке принятых кружочков;
- ошибки подготовки: причина и retry;
- настройки: режим модерации, громкость, лимиты, цвета, фон;
- режим показа: автопоказ или интерактивная стена;
- диагностика: Telegram, worker, FFmpeg/ffprobe, экран.

Предпросмотр в панели по умолчанию muted. Закрытие модального предпросмотра останавливает video element.

## Операторская Стена

Этап 7 добавляет стену статичных превью на `/screen` и управление составом в `/admin`.

- Стена строится сервером из таблицы `wall_items`, связанной с ready+approved `Submission`.
- На экране отображается до 12 элементов стены; тринадцатый элемент сервер не добавляет.
- Повторный показ того же `Submission` не меняет стену и не создаёт второй элемент.
- `skipped`, `failed` и `cancelled` показы не меняют состав стены.
- Оператор может добавить или убрать поздравление со стены; файлы и история при этом сохраняются.
- `/screen` только отображает массив `wall` из snapshot и не вычисляет состав стены самостоятельно.

Файлы хранятся внутри `data/`:

```text
data/
  app.sqlite3
  events/
    <event_id>/
      originals/
      playback/
      thumbnails/
      background/
  temp/
  logs/
```

База хранит относительные пути внутри `data/`.

Пути строятся только из внутренних ID. Пользовательский ввод, имена гостей и Telegram-имена не используются как имена файлов.

До завершения обработки файлы находятся в `data/temp/`. Подготовленные файлы переносятся в папку мероприятия только после успешного ffprobe/FFmpeg/thumbnail этапов.

## Восстановление после перезапуска

При старте приложение должно:

- проверить структуру `data/`;
- открыть SQLite и применить миграции;
- очистить устаревшие временные файлы;
- вернуть `downloading` и `processing` работы в состояние, пригодное для повторной обработки;
- перевести незавершённый `playing` ролик обратно в `queued`;
- остановить общий показ до команды оператора;
- сохранить мероприятия, настройки, модерацию, очередь, историю и стену.

На этапе 8 при старте также удерживается process lock в `data/app.lock`, чтобы второй экземпляр приложения не начал параллельно читать Telegram и менять очередь. Lock освобождается при штатном завершении процесса.

Папка `data/temp` очищается при старте до запуска фоновой обработки. Долговременные файлы, доступные для показа, уже находятся в папке мероприятия, поэтому очистка временных неполных файлов не удаляет готовые ролики.

Рабочая временная папка ролика удаляется также после ошибки и отмены обработки. Перед публикацией worker повторно проверяет существование отправки; удаление оператором во время скачивания или FFmpeg не должно создавать файлы без записи в базе. Если перенос подготовленных файлов завершился частично, неопубликованные результаты удаляются. Отмена worker завершает запущенный FFmpeg/ffprobe и дожидается освобождения его stdout/stderr до очистки файлов.

Каждый snapshot читает версию, мероприятие, очередь, историю и стену в одной read-транзакции SQLite. WebSocket-рассылка использует фиксированный список получателей и параллельные отправки с тайм-аутом 1 секунда на клиента; ошибка или задержка одного клиента не срывает доставку остальным. Worker изолирует ошибки уведомления от обработки уже взятого задания.

Диагностика включает свободное место на диске. Если свободного места меньше `MIN_FREE_DISK_MB`, новые Telegram-кружочки не принимаются и не расходуют лимит гостя; оператор видит состояние диска в `/admin`.

## Запуск и desktop-оболочка

`start_visual_pozdr.bat` остаётся способом запуска исходной browser-версии и резервной диагностикой. Этап 11 добавляет Electron-оболочку для Windows.

Electron запускает ровно один локальный backend на `127.0.0.1`, дожидается `GET /api/health`, затем открывает окно оператора с `/admin`. Экран трансляции открывается отдельным бескаркасным fullscreen `BrowserWindow` с `/screen`; повторное открытие переводит в фокус существующее окно, а не создаёт второй экран. Выбор монитора не перемещает окно до отдельной команды «Переместить экран»; при переносе main process временно выходит из fullscreen, переносит окно по рабочей области монитора и снова включает fullscreen. React продолжает обращаться к FastAPI через относительные HTTP, WebSocket и media URL; Electron не содержит правил очереди или playback.

Панель `/admin` в Electron получает через preload только безопасные сведения о дисплеях: ID, имя, границы, рабочую область, масштаб и признак основного. Выбор монитора, расчёт координат, открытие, перенос и закрытие `ScreenWindow` выполняются только main process. Если выбранный дисплей отключён, main process переводит окно на основной дисплей и передаёт панели предупреждение. В browser-режиме preload отсутствует: панель явно сообщает об отсутствии desktop-управления, а «Открыть в браузере» сохраняет прежний сценарий новой вкладки. Закрытие `ScreenWindow` запускает существующий вызов `/api/screen/{screen_id}/release`; серверная защита единственного активного экрана остаётся обязательной.

В упакованной версии SQLite, медиа, `.env` и логи находятся в `%APPDATA%/Visual Pozdr/` вне ASAR: `.env` — в корне, SQLite и медиа — в `data/`, startup-лог backend — в `logs/backend.log`. При первом запуске новая папка автоматически получает содержимое старой `%APPDATA%/visual-pozdr-frontend/`, если она существует. Python-backend поставляется отдельным ресурсом `resources/backend/visual-pozdr-backend.exe`, а собранный frontend находится в `resources/frontend/dist/` и передаётся FastAPI через `FRONTEND_DIST_DIR`. FFmpeg и ffprobe находятся в `resources/runtime/ffmpeg/`. Перед запуском Electron проверяет все эти обязательные ресурсы и локальный порт: при занятом `8000` другим приложением packaged-версия выбирает первый свободный порт из диапазона `8001`–`8020`; если на выбранном порту уже отвечает Visual Pozdr, второй backend не запускается. Затем Electron запускает backend дочерним процессом, ожидает `GET /api/health` и только затем открывает `AdminWindow`. `ScreenWindow` открывается только оператором из панели. При завершении Electron ожидает остановку дочернего backend и принудительно завершает его дерево только как fallback. Renderer не получает Node.js-доступ: включены `contextIsolation` и sandbox, а preload предоставляет только ограниченные desktop-команды.

FFmpeg runtime находится в `runtime/ffmpeg/` исходного проекта и включается в Windows-инсталлятор как `resources/runtime/ffmpeg/`. В packaged-режиме Electron передаёт backend абсолютные `FFMPEG_PATH` и `FFPROBE_PATH`; эти бинарники имеют приоритет над системным `PATH`. В browser/dev-режиме backend сначала использует `runtime/ffmpeg/`, затем системный `PATH`. Диагностика `/admin` показывает состояние, версию и путь обоих инструментов. Если оба инструмента недоступны, worker остаётся в `tools_missing` с явной причиной, не меняя статусы обработки роликов.

Перед стартом `.bat` запускает `scripts/preflight_check.py`, который проверяет:

- наличие `.env`;
- локальный `HOST=127.0.0.1`;
- корректность и доступность `PORT`;
- наличие `frontend/dist/index.html`;
- доступность `DATA_DIR` и свободное место относительно `MIN_FREE_DISK_MB`;
- наличие Telegram-настроек как предупреждение, а не как блокер;
- наличие `ffmpeg` и `ffprobe` как предупреждение, потому что сервер может стартовать без подготовки новых видео.

Если preflight находит блокирующие ошибки, сервер не запускается и оператор получает понятное сообщение в окне `.bat`. Если есть только предупреждения, запуск продолжается.

Перед упаковкой desktop-версии нужно собрать `frontend/dist` и PyInstaller backend. Команда `npm run desktop:package:portable` из `frontend/` создаёт единый `artifacts/portable/VisualPozdr.exe`; для его запуска на ноутбуке мероприятия не нужны Python, Node.js, PowerShell или установленный FFmpeg. FFmpeg/ffprobe поставляются внутри Electron-ресурсов; `.bat` остаётся резервным способом запуска разработки и диагностики.

Electron main/preload используют только Node.js built-ins, Electron и локальные `.cjs`-модули. React, React DOM и QRCode выполняются в браузерном bundle, собранном Vite; они и инструменты сборки находятся в `devDependencies` и не поставляются отдельным `node_modules` в desktop-приложении. Для сборки исходников устанавливаются все зависимости через `npm ci` (без `--omit=dev`). Контрольная команда `npm run desktop:package:audit` создаёт распакованное приложение в `artifacts/size-audit/win-unpacked/`, не заменяя ранее сохранённые installer/portable-сборки. Результаты измерений и проверки находятся в `docs/SIZE_AUDIT.md`.

Штатная остановка desktop-backend выполняется через приватный stdin pipe дочернего процесса: Electron передаёт `shutdown`, после чего Uvicorn выполняет lifespan cleanup, останавливает worker и Telegram и освобождает `app.lock`. Закрытие pipe также запрашивает остановку. Канал включается только переменной `VISUAL_POZDR_DESKTOP_CONTROL=1`; browser-запуск сохраняет управление через терминал. Electron ждёт до 10 секунд; принудительное завершение дерева процессов используется только при зависании. Публичного HTTP endpoint остановки нет.

Диагностика Telegram-бота должна показывать не только наличие токена, но и состояние polling-задачи: `not_configured`, `not_started`, `starting`, `running`, `error` или `stopped`. При ошибке polling сервер сохраняет короткий текст ошибки в `bot_error` и пытается перезапустить polling без остановки приложения.

## macOS demo: платформенная поставка

Mac-версия использует тот же React, Telegram-приём, SQLite, worker и серверное управление показом.
`frontend/electron/platform.cjs` выбирает имена исполняемых файлов, Python virtualenv и native runtime.
На Windows сохранены `.exe` и `.venv/Scripts/python.exe`; на Mac — файлы без `.exe` и `.venv/bin/python`.
В исходниках macOS-инструменты разделены на `runtime/ffmpeg/darwin-arm64/` и `darwin-x64/`,
в `.app` попадает только нужная архитектура как `Contents/Resources/runtime/ffmpeg/`.
Backend — `Contents/Resources/backend/visual-pozdr-backend`, frontend — `Contents/Resources/frontend/dist/`.

`scripts/build_mac_media.py` собирает FFmpeg 7.1.1 и x264 из закреплённых исходников с проверкой
SHA-256, без зависимостей от Homebrew-библиотек. Проверяются dylib-зависимости, H.264/AAC и JPEG;
исходные URL, контрольные суммы и GPL-лицензии включены рядом с бинарниками. Для demo x264
собирается без ассемблерных оптимизаций для воспроизводимой сборки обеих архитектур; настройки
транскодирования worker не меняются. Производительность подготовки оценивается на целевом Mac.

Пользовательский каталог определяется Electron `userData`: на macOS это
`~/Library/Application Support/Visual Pozdr/`. Личный `.env` создаётся из пустого шаблона,
бот начинает работать после заполнения токена/username и перезапуска. Ни сборка, ни GitHub
не получают пользовательский Telegram-токен. Повторное использование одного токена в двух
одновременно работающих long-polling приложениях не поддерживается.

На POSIX backend запускается в отдельной process group. Сначала отправляется существующая
команда `shutdown` через stdin; при зависании завершается группа, включая дочерний FFmpeg.
Windows fallback остаётся `taskkill`. При переносе fullscreen-окна на Mac main process ждёт
`leave-full-screen` и только после этого меняет bounds; переносы сериализуются. Признак
основного дисплея определяется сравнением ID с `screen.getPrimaryDisplay()`.

Workflow `.github/workflows/mac-demo.yml` запускается вручную на нативных macOS runners
для arm64/x64, собирает ZIP и выполняет backend/desktop-тесты, packaged smoke, GUI-проверку
обеих тем/QR и ZIP roundtrip. В CI используется временный профиль (`--smoke-test` вместе
с `VISUAL_POZDR_SMOKE_PROFILE`), пустой токен и синтетическое мероприятие. Пользовательские данные
не затрагиваются. Поставка демо ad-hoc подписана, но не имеет Developer ID и notarization.
Объявленный минимум — macOS 13; целевая Golden Gate 27.0.1 требует отдельной ручной приёмки.
Артефакты сборки не коммитятся и скачиваются в `artifacts/mac-demo/`.

## Темы экрана

Этап 10 добавляет frontend-темы для `/screen` без изменения backend-правил очереди, playback и API стены.

Темы на frontend-уровне:

- `new_year` — «Новогоднее настроение», основная визуальная тема с готовыми PNG из `frontend/public/themes/new_year/`;
- `neutral` — «Нейтральный», тема с PNG-фоном, отдельным слоем рабочей зоны и рамкой для круглых элементов из `frontend/public/themes/neutral/`.

Значение темы хранится в `events.theme`. Старое значение `simple_new_year` нормализуется в `new_year` при старте/чтении состояния, чтобы существующие мероприятия продолжили открываться в новогоднем оформлении.

Ассеты `new_year`:

- `background.png` (`1672x941`) — основной фон;
- `tree-overlay.png` (`1261x1247`) — декоративный слой ёлки;
- `ornament.png` (`1254x1254`) — рамка для элементов стены.

Ассеты `neutral`:

- `background.png` (`1698x926`) — основной нейтральный фон;
- `zone-overlay.png` (`1392x1130`) — прозрачный декоративный слой нейтральной темы;
- `circle-frame.png` (`1254x1254`) — рамка для круглых превью.

`/screen` получает состав стены только из server snapshot `state.wall`. Позиции шариков заданы в конфигурации frontend-темы, не генерируются случайно и не влияют на порядок очереди или playback.

Смена `events.theme` изменяет визуальное окружение, но не пересоздаёт HTML-видео текущего ролика: `playback_id`, источник, позиция и воспроизведение сохраняются.

Каждая тема хранит единственный набор из 12 slot-позиций. В `new_year` позиции привязаны к области ёлки. В `neutral` позиции образуют равномерную сетку 3×4 в рабочей зоне справа.

В режиме `interactive_wall` темы используют тот же `state.wall`, что и `auto_loop`; клик по элементу стены запускает выбранный `Submission` через сервер. В `new_year` геометрия шариков привязана к области ёлки. В `neutral` элементы отображаются как круглые превью с рамкой `circle-frame.png` в правой рабочей зоне; `zone-overlay.png` — PNG размера `1698×926` с белым прямоугольником прозрачностью 45% и шириной 35% фона.

Анимации реализованы через CSS `transform` и `opacity`. Для `prefers-reduced-motion: reduce` бесконечное покачивание отключается.

## Безопасность и локальный доступ

Сервер слушает только `127.0.0.1`.

Токен Telegram-бота хранится в серверной конфигурации и не передаётся в браузер.

Логи не должны содержать токены, полные секреты или произвольные пользовательские пути.

Нужен `.env.example` без секретов.

HTTP и WebSocket должны проверять допустимый Origin/Host для локального доступа.

Доступ с телефона по Wi-Fi не входит в первую версию.
