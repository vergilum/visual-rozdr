# Задачи Этапа 11: Приёмочная Готовность

Дата составления: 2026-10-16.

## Цель

Подготовить текущую локальную версию к первому реальному мероприятию: подтвердить работу с Telegram и проектором, устранить расхождения документации и закрыть известные эксплуатационные недочёты. Этап не добавляет облачный доступ, вебхуки, мобильное управление, ИИ-модерацию или новые режимы стены.

## Порядок Выполнения

### 1. Провести Приёмочный Прогон

Приоритет: критический.

- Выполнить весь список из `docs/NEXT_SESSION_HANDOFF.md` на реальном Telegram-аккаунте.
- Проверить `/screen` на целевом проекторе или мониторе в темах `new_year` и `neutral`.
- Проверить звук, полноэкранный режим, отсутствие прокрутки, повтор ролика, закрытие ролика и переключение между экранами.
- Зафиксировать обнаруженные симптомы, разрешение экрана и шаги воспроизведения в отдельном отчёте.

Готово, когда: сценарий проходит без блокирующих ошибок либо для каждой ошибки есть отдельная задача с шагами воспроизведения.

### 2. Привести Документацию К Одним Правилам

Приоритет: критический.

- Обновить `README.md`: заменить заголовок проверки этапа 9 на этап 10 и убрать устаревшее ожидание ответа бота о немедленном начале подготовки до выбора стола.
- Обновить `docs/FINAL_SMOKE_TEST.md`: указать этап 10 и ручное добавление ролика на стену оператором.
- Обновить `docs/STAGE_4_WINDOWS_CHECK.md`: автоматическая модерация одобряет ролик, но не добавляет его в очередь и на стену.
- Уточнить назначение `docs/STAGE_10_VISUAL_THEME_CHECK.md`: документ должен охватывать обе темы.
- После каждого изменения поведения одновременно обновлять `SPEC.md`, `ARCHITECTURE.md`, `README.md` или соответствующую операционную инструкцию.

Готово, когда: все инструкции описывают один и тот же процесс: выбор стола, подготовка, модерация, ручное добавление на стену и показ.

### 3. Дать Гостю Результат Отправки

Приоритет: высокий.

- После выбора стола отправлять гостю подтверждение о принятии ролика в обработку.
- После успешной подготовки отправлять нейтральное сообщение о передаче ролика оператору.
- После технической ошибки отправлять понятное сообщение без внутренних деталей и с предложением отправить новый кружочек.
- Не отправлять повторные сообщения при повторной доставке Telegram-update или повторной обработке одного и того же задания.
- Добавить тесты для всех трёх исходов.

Готово, когда: гость получает ровно одно соответствующее статусу сообщение, а API, очередь и worker остаются неблокирующими.

### 4. Закрыть Незаполненные Настройки И Жизненный Цикл Экрана

Приоритет: высокий.

- Реализовать явный вызов `POST /api/screen/{screen_id}/release` при закрытии или выгрузке `/screen`; сохранить heartbeat timeout как резервный механизм.
- Для настроек `primary_color`, `accent_color`, `transition_seconds` и фонового изображения выбрать одно решение: применить их на экране или удалить из API, БД и панели как неиспользуемые.
- Если фон используется, выдавать его только из папки мероприятия внутри `data/` и не менять существующую геометрию тем без проверки на проекторе.
- Добавить автоматические тесты release активного экрана и выбранного решения для настроек.

Готово, когда: закрытая активная вкладка освобождает экран сразу, а каждая отображаемая в панели настройка реально влияет на результат или отсутствует.

### 5. Усилить Эксплуатационную Надёжность

Приоритет: средний.

- Реализовать запись значимых операторских и системных действий в уже существующий `audit_entries`: модерация, изменение стены, команды показа, удаление и смена настроек.
- Либо реализовать `VIDEO_WORKER_CONCURRENCY` с безопасным ограничением числа воркеров, либо удалить неработающую настройку из конфигурации и документации.
- Добавить в preflight проверку доступности Telegram только как предупреждение, не блокирующее офлайн-показ уже подготовленных роликов.
- Проверить восстановление после принудительного закрытия приложения: текущий ролик возвращается в очередь, показ остановлен, временные файлы очищены.

Готово, когда: действия оператора можно проследить, конфигурация не содержит фиктивных параметров, а сценарий восстановления подтверждён тестом и ручной проверкой.

### 6. Минимальная Инженерная Автоматизация

Приоритет: средний.

- Добавить frontend-проверки: как минимум typecheck, lint и production build в одном воспроизводимом npm-скрипте.
- Добавить CI-проверку backend-тестов и frontend-сборки при появлении Git-репозитория.
- Инициализировать Git-репозиторий, добавить `.gitignore` для `.env`, `data/`, `.venv/`, `node_modules/`, `frontend/dist/`, кэшей и локальных артефактов.
- Не добавлять в Git Telegram-токен, базу SQLite или медиа гостей.

Готово, когда: чистая рабочая копия может проверить backend и frontend понятными командами, а секреты и данные мероприятия исключены из контроля версий.

## После Этапа 11

Рассматривать только после успешного мероприятия:

- архивирование и управление старыми мероприятиями;
- аккуратное модальное подтверждение вместо `window.confirm`;
- локальная сессия доступа для `/admin` и `/screen` с использованием `LOCAL_SESSION_SECRET`;
- отдельные версионируемые миграции SQLite;
- расширение лимитов, аналитики и отчётов по столам.

## Проверка Результата

```powershell
py -m pytest backend/tests

cd frontend
npm run build
cd ..

py scripts/preflight_check.py
```

После автоматических проверок выполнить ручной прогон из `docs/NEXT_SESSION_HANDOFF.md` и записать результат в отчёт этапа.
